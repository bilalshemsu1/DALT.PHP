Our workspace flow works, but the data belongs to one browser session. Open the app
in a private window and the list is empty. In this lesson we will give workspaces to
the application instead: we will create a database table, insert each workspace into
it, and load the list from it on every request.

We will begin with SQLite. It keeps the whole database in one local file, so we can
learn the application's data flow without installing a database server. When our
product needs PostgreSQL later, the boundary we build here will still make sense.

## Point DALT at the local database

Open `.env` and find the database settings. The default DALT project already
contains the SQLite values; make sure they are active and not commented out:

```dotenv
DB_DRIVER=sqlite
DB_DATABASE=database/app.sqlite
```

`.env` is local configuration. It tells this copy of the application which database
to use, while `.env.example` documents the defaults for a new copy. Git ignores the
real `.env` because another environment may need different settings.

The database file will be `database/app.sqlite`. DALT creates it when it first
connects, and Git ignores it too. We will version the instructions that shape the
database, not one developer's data.

## Describe the workspaces table

Create `database/migrations/002_create_workspaces_table.sql`:

```sql
CREATE TABLE workspaces (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name VARCHAR(50) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

A migration is a saved database change. Keeping it as a file means a new checkout
can build the same table instead of receiving our current database file.

This table gives every workspace three facts:

- `id` is a unique number generated by SQLite;
- `name` is required and has the same 50-character limit as our form;
- `created_at` records when the row was inserted.

The filename begins with `002` so it runs after DALT's existing `001` migration.
Now apply every migration that has not run yet:

```bash
php artisan migrate
```

On a fresh project, the result is:

```text
Running migration: 001_create_users_table.sql
✓ Success
Running migration: 002_create_workspaces_table.sql
✓ Success

Ran 2 migrations.
Migration process completed.
```

If the users migration had already run in your copy, only the workspace migration
appears. DALT records completed filenames in a `migrations` table and skips them on
future runs.

## Insert a workspace instead of storing an array

Open `app/Http/controllers/workspaces/store.php`. Add the database class beside the
existing imports:

```php
use CoreApp;
use Core\Database;
use Core\Request;
use Core\Session;
use Core\ValidationException;
use Core\Validator;
```

Keep the request reading and validation we wrote in the previous lesson. Replace
the session-array block below the validation with this database insert:

```php
$database = App::resolve(Database::class);
$database->query(
    'INSERT INTO workspaces (name) VALUES (:name)',
    ['name' => $name],
);
```

The container gives us DALT's configured `Database` connection. The SQL names the
table and column we want to change. `:name` is a placeholder; the second argument
binds the submitted value to it separately.

Keep values out of the SQL string itself. A workspace name such as `Sam's team`
contains punctuation that should remain data, not become part of the SQL command.
The bound parameter lets the database driver handle that boundary safely.

Leave the end of the controller as it is:

```php
Session::flash('success', "{$name} was created.");

return redirect('/', 303);
```

The success notice still belongs to the browser that submitted the form, so flash
data remains a good use of the session. The workspace itself now belongs to the
application, so it belongs in the database.

## Load every workspace from the table

Our GET controller still reads the old session array. Replace
`app/Http/controllers/welcome.php` with:

```php
<?php

declare(strict_types=1);

use Core\App;
use Core\Database;

$database = App::resolve(Database::class);
$workspaces = $database
    ->query('SELECT id, name FROM workspaces ORDER BY id DESC')
    ->get();

view('welcome.view.php', ['workspaces' => $workspaces]);
```

`SELECT id, name FROM workspaces` asks for exactly the fields our page currently
uses. `ORDER BY id DESC` puts the most recently inserted row first. `get()` returns
all matching rows as an array, which is already the shape our view loops over.

Nothing in `resources/views/welcome.view.php` needs to know whether that array came
from a session or a database. The controller changed the source while preserving
the view's input. That small boundary lets us improve storage without rebuilding the
screen.

## See application-owned data

Refresh the app and create a workspace named `Database Space`. The same visible
flow still happens: the POST validates, inserts one row, flashes a notice, and
redirects to the GET page. Refresh again and the notice disappears while the row
remains.

Now open the app in a private window or a different browser. `Database Space` is
still in the list. This new browser has a different session and does not receive the
old success notice, but both sessions read the same application database.

Run the migration command once more:

```bash
php artisan migrate
```

DALT now reports:

```text
No migrations to run.
Migration process completed.
```

Migrations are not scripts we replay on every request. Each one is an ordered,
versioned change that DALT applies once to a particular database.

If you are using Git, save the migration and the two controller changes:

```bash
git add database/migrations/002_create_workspaces_table.sql app/Http/controllers/welcome.php app/Http/controllers/workspaces/store.php
git commit -m "Persist workspaces in the database"
```

Do not add `.env` or `database/app.sqlite`; they are local runtime files and are
already ignored.

Our workspaces now survive browser sessions, but every row is still only text on the
home page. Next, we will make a workspace a destination of its own so the product
has somewhere to add projects and issues.
