DALT now opens PostgreSQL, but that database contains only our disposable volume
probe. We will use this empty-target moment to express the schema in PostgreSQL's own
types. We are porting the tables we already earned—not designing memberships, labels,
or comments early.

## Reset the disposable PostgreSQL target

Lesson 34 created `lesson_34_probe` only to prove volume persistence. Remove this
Compose project's database volume and start a genuinely empty server:

```bash
docker compose down --volumes
docker compose up -d db
docker compose ps
```

The first PostgreSQL 18 initialization can take several seconds. Do not migrate while
the status says `health: starting`; run `docker compose ps` again until it says
`healthy`, then confirm the connection:

```bash
php scripts/database-status.php
```

This is the one safe moment to rewrite our five migration files: they have been used
by the old SQLite database, but have never been applied to this new PostgreSQL target.
After PostgreSQL records them, schema changes will always use new migration files.

## Port users and timestamps

Replace `database/migrations/001_create_users_table.sql` with:

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

`GENERATED BY DEFAULT AS IDENTITY` lets PostgreSQL generate normal IDs while still
allowing our one-time importer to preserve explicit SQLite IDs. `TIMESTAMPTZ` stores an
instant with timezone-aware input/output behavior; it is a safer application timestamp
than SQLite's untyped `DATETIME` spelling.

The email uniqueness already exists in our product, so it remains here. We will add
the constraints SQLite did not enforce in the next lesson.

## Port the current hierarchy

Replace `002_create_workspaces_table.sql`:

```sql
CREATE TABLE workspaces (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Replace `003_create_projects_table.sql`:

```sql
CREATE TABLE projects (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id BIGINT NOT NULL,
    name VARCHAR(60) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX projects_workspace_id_index
ON projects (workspace_id);
```

Replace `004_create_issues_table.sql`:

```sql
CREATE TABLE issues (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id BIGINT NOT NULL,
    title VARCHAR(100) NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    status VARCHAR(20) NOT NULL DEFAULT 'open',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX issues_project_id_index
ON issues (project_id);
```

The relationship columns are now the same `BIGINT` family as the IDs they will
reference. We retained the existing lookup indexes. Foreign keys and status/name
checks are deliberately the next migration, where we can prove each new defense
separately.

## Keep ownership as its own historical step

Replace `005_add_owner_to_workspaces_table.sql`:

```sql
ALTER TABLE workspaces ADD COLUMN owner_id BIGINT;

CREATE INDEX workspaces_owner_id_index
ON workspaces (owner_id);

UPDATE workspaces
SET owner_id = (SELECT id FROM users ORDER BY id LIMIT 1)
WHERE owner_id IS NULL;
```

The update finds no rows in a fresh target, but retaining it keeps the migration's
original story visible: ownership was added after workspaces already existed. The
importer will supply real owners before we require `NOT NULL`.

## Let DALT apply the PostgreSQL SQL

Run the migrations:

```bash
php artisan migrate
```

DALT should list migrations 001 through 005 and finish with:

```text
Ran 5 migrations.
Migration process completed.
```

Run the command again:

```bash
php artisan migrate
```

This time it should say `No migrations to run.` The `migrations` table is durable
history, not a guess based on whether a table happens to exist.

Inspect the result using the `psql` client already inside the container:

```bash
docker compose exec -T db \
  psql -U dalt -d dalt_issue_tracker -c '\dt'

docker compose exec -T db \
  psql -U dalt -d dalt_issue_tracker -c '\d users'
```

The first command lists `users`, `workspaces`, `projects`, `issues`, and `migrations`.
The second shows a bigint identity primary key, timezone-aware timestamps, and the
unique email constraint.

```bash
git add database/migrations
git commit -m "Port the schema to PostgreSQL"
```

Our empty PostgreSQL database now has the same application shape as SQLite. It still
accepts relationships and values that our PHP would reject. Next we will make the
database itself defend those current invariants before importing a single row.
