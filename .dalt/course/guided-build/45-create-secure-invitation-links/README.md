# Create secure invitation links

Owners can see their team, but they cannot add anyone. We will create a seven-day
invitation link, reveal its secret token to the owner once, and store only a hash in
PostgreSQL. This project uses copyable links so we can teach the complete invitation
lifecycle without introducing an email provider.

## Store an invitation without storing its secret

Create `database/migrations/008_create_workspace_invitations_table.sql`:

```sql
CREATE TABLE workspace_invitations (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id BIGINT NOT NULL,
    email VARCHAR(254) NOT NULL,
    inviter_id BIGINT NOT NULL,
    role VARCHAR(20) NOT NULL DEFAULT 'member',
    token_hash CHAR(64) NOT NULL,
    expires_at TIMESTAMPTZ NOT NULL,
    accepted_at TIMESTAMPTZ NULL,
    revoked_at TIMESTAMPTZ NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
```

Add foreign keys from `workspace_id` and `inviter_id`, both with cascading deletion.
Then constrain the values:

```sql
CONSTRAINT workspace_invitations_role_check
    CHECK (role IN ('owner', 'member')),
CONSTRAINT workspace_invitations_email_normalized_check CHECK (
    email = lower(email)
    AND email = btrim(email)
    AND char_length(email) BETWEEN 3 AND 254
),
CONSTRAINT workspace_invitations_token_hash_unique
    UNIQUE (token_hash),
CONSTRAINT workspace_invitations_expiry_check
    CHECK (expires_at > created_at),
CONSTRAINT workspace_invitations_single_resolution_check CHECK (
    accepted_at IS NULL OR revoked_at IS NULL
)
```

The last check prevents one invitation being both accepted and revoked. Add a partial
unique index for unresolved invitations:

```sql
CREATE UNIQUE INDEX workspace_invitations_active_email_unique
    ON workspace_invitations (workspace_id, email)
    WHERE accepted_at IS NULL AND revoked_at IS NULL;

CREATE INDEX workspace_invitations_workspace_created_index
    ON workspace_invitations (workspace_id, created_at DESC);
```

One workspace cannot accumulate several pending links for the same normalized email.
Accepted and revoked history remains available. Run `php artisan migrate`.

## Add owner-only invitation endpoints

In `routes/routes.php`, add:

```php
$router->get(
    '/api/workspaces/{workspace}/invitations',
    'api/invitations/index.php',
)->only(ApiAuth::class);

$router->post(
    '/api/workspaces/{workspace}/invitations',
    'api/invitations/store.php',
)->only([ApiAuth::class, 'csrf']);
```

Both controllers call `WorkspaceAccess::findOrFail` with
`WorkspaceAccess::MANAGE_MEMBERS`. A member receives 403; an outsider still receives
404.

In `api/invitations/index.php`, select only display fields. Derive status from durable
timestamps:

```sql
CASE
    WHEN accepted_at IS NOT NULL THEN 'accepted'
    WHEN revoked_at IS NOT NULL THEN 'revoked'
    WHEN expires_at <= CURRENT_TIMESTAMP THEN 'expired'
    ELSE 'pending'
END AS status
```

Return `id`, `email`, `role`, `status`, `expiresAt`, and `createdAt`. Never return
`token_hash`; it is not useful to the browser and must not become an alternate secret.

## Generate and hash the raw token

In `api/invitations/store.php`, normalize email, validate it with DALT's validator,
and require `owner` or `member` as the requested role. Do not query the users table.
The public response should be identical whether that email already has an account or
not.

Generate 32 cryptographically secure bytes and encode them for a URL:

```php
$rawToken = bin2hex(random_bytes(32));
$tokenHash = hash('sha256', $rawToken);
```

The raw token is a bearer credential: anyone holding it can attempt acceptance. Like
a password, the database should not need the original value.

Inside `Transaction::run`, first resolve any expired active invitation:

```php
$database->query(
    'UPDATE workspace_invitations
     SET revoked_at = CURRENT_TIMESTAMP
     WHERE workspace_id = :workspace_id
       AND email = :email
       AND accepted_at IS NULL
       AND revoked_at IS NULL
       AND expires_at <= CURRENT_TIMESTAMP',
    [
        'workspace_id' => $workspace['id'],
        'email' => $email,
    ],
);
```

If an unresolved row still exists, return a 422 email error saying a pending
invitation already exists. Otherwise insert the hash and expiry:

```php
$database->query(
    "INSERT INTO workspace_invitations
        (workspace_id, email, inviter_id, role,
         token_hash, expires_at)
     VALUES (:workspace_id, :email, :inviter_id, :role,
             :token_hash,
             CURRENT_TIMESTAMP + INTERVAL '7 days')",
    [
        'workspace_id' => $workspace['id'],
        'email' => $email,
        'inviter_id' => $inviterId,
        'role' => $role,
        'token_hash' => $tokenHash,
    ],
);
```

The partial unique index remains the final concurrency defense even if two requests
perform the PHP pre-check together.

Return the public invitation plus this one-time field:

```php
'inviteUrl' => '/invitations/' . $rawToken,
```

Future list requests cannot reconstruct the URL. Losing it means revoking or waiting
for expiry and creating another, not reading the secret back from PostgreSQL.

## Validate invitation JSON in React

Create `resources/app/invitations-data.ts`. Define `Invitation` with the two roles and
four statuses as unions. Parse every unknown row, just as we did for members.

Add `fetchInvitations(workspaceId, signal)` for the owner list and
`createInvitation(workspaceId, csrfToken, email, role)` for the protected form.
When the server returns 422, throw an `InvitationValidationError` containing the
email or role message. On 201, require a valid invitation, string `inviteUrl`, and
string `message`.

## Add the owner invitation panel

Create `resources/app/InvitationPanel.tsx`. Load invitation history in an effect. The
form has an email input, an owner/member select, and a `Create link` button. Preserve
email when validation fails.

After a successful request, prepend only the confirmed invitation and construct the
copyable URL from the current origin:

```tsx
const result = await createInvitation(
  data.workspace.id,
  data.form.csrfToken,
  email,
  role,
)

setInvitations((current) => [
  result.invitation,
  ...(current ?? []),
])
setInviteUrl(window.location.origin + result.inviteUrl)
setEmail('')
```

Render the new URL in a read-only input so manual copying always works. A `Copy link`
button may call `navigator.clipboard.writeText`; report a useful manual-copy message
if browser permission rejects it.

Show the invitation list with visible email, role, and status words. Then mount the
panel from `MembersPage.tsx` only for owners:

```tsx
{data.workspace.role === 'owner'
  && <InvitationPanel data={data} />}
```

Members do not see an unusable form, but the server capability check still protects
the endpoints.

## Prove token secrecy and role boundaries

Extend the authorization feature test. Create an invitation as an owner, extract the
raw token from the returned link, and load the stored row:

```php
expect($stored['token_hash'])
    ->toBe(hash('sha256', $rawToken))
    ->not->toBe($rawToken);
```

Require that neither the create response's public invitation nor the list response
contains `tokenHash`, the raw token, or its stored hash. A normalized duplicate must
return 422. Add the requester as a member and prove a new invitation attempt returns
403.

In `resources/app/invitation-workflow.test.tsx`, use MSW to prove the CSRF token and
email are submitted, the one-time URL appears after 201, and pending status is visible.
A second test returns the duplicate 422 response and proves the input remains editable
with its server message.

Run:

```bash
php artisan test tests/Feature/WorkspaceAuthorizationTest.php
npm run typecheck
npm run lint
npm test -- --run
npm run build
```

The backend passes seven tests with 66 assertions, and React passes 24 tests across
seven files. We can now create a secure link, but following it is intentionally our
next product step: verify its token and account before granting membership exactly
once.
