# Record meaningful activity history

The issue now changes through many routes. We will create one append-only timeline so
the team can answer what changed and who changed it—without storing presentation
sentences that become impossible to reword or translate.

> **Helpful background:** PostgreSQL explains why grouped statements succeed or roll
> back together in [Transactions](https://www.postgresql.org/docs/18/tutorial-transactions.html),
> and documents structured [`jsonb`](https://www.postgresql.org/docs/18/datatype-json.html)
> storage separately from ordinary text.

## Store event facts, not English sentences

Create `database/migrations/013_create_issue_activity.sql`:

```sql
CREATE TABLE issue_activity (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    issue_id BIGINT NOT NULL,
    actor_id BIGINT NULL,
    event_type VARCHAR(40) NOT NULL,
    metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT issue_activity_issue_foreign
        FOREIGN KEY (issue_id) REFERENCES issues(id) ON DELETE CASCADE,
    CONSTRAINT issue_activity_actor_foreign
        FOREIGN KEY (actor_id) REFERENCES users(id) ON DELETE SET NULL,
    CONSTRAINT issue_activity_metadata_object_check
        CHECK (jsonb_typeof(metadata) = 'object')
);
```

Add a check listing the event types our product emits: issue creation, status,
assignment, priority, due date, labels, comment added, and comment deleted. Add
`(issue_id, created_at, id)` for stable timeline order.

An actor is nullable because history can remain useful after account deletion. The
metadata object stores event-specific facts such as `{"from":"open","to":"closed"}`.
It does not duplicate issue titles, actor names, or a rendered sentence.

Run `php artisan migrate`.

## Add one small recording seam

Create `app/Support/Activity.php`:

```php
public static function record(
    Database $database,
    int $issueId,
    ?int $actorId,
    string $type,
    array $metadata = [],
): void {
    $database->query(
        'INSERT INTO issue_activity
            (issue_id, actor_id, event_type, metadata)
         VALUES
            (:issue_id, :actor_id, :event_type, CAST(:metadata AS JSONB))',
        [
            'issue_id' => $issueId,
            'actor_id' => $actorId,
            'event_type' => $type,
            'metadata' => json_encode((object) $metadata, JSON_THROW_ON_ERROR),
        ],
    );
}
```

Casting the empty PHP array to an object is important: `[]` is a JSON array and our
constraint correctly rejects it, while `{}` is an empty metadata object.

## Make history part of the business change

Issue creation was one insert. It is now two writes, so wrap both:

```php
$issueId = Transaction::run($database, function () use ($database, $actorId): int {
    // Insert the issue with its validated fields.
    $id = (int) $database->getConnection()->lastInsertId();
    Activity::record($database, $id, $actorId, 'issue.created');
    return $id;
});
```

Do the same for status changes, issue planning edits, and comment creation/deletion.
The update controller already replaces labels in a transaction, so compare old and
new values there and append events before commit:

```php
if ($issue['priority'] !== $planning['priority']) {
    Activity::record($database, (int) $issue['id'], $actorId, 'priority.changed', [
        'from' => $issue['priority'],
        'to' => $planning['priority'],
    ]);
}
```

Apply the same shape to assignment and due date. Sort old and new label IDs before
comparison; selection order is not a product change. A repeated status request and an
edit that keeps the same values record nothing.

The order inside every controller remains deliberate:

1. authorize the nested resource;
2. validate all input;
3. begin the transaction;
4. change business state and append its events;
5. commit together.

An outsider fails at step one. Invalid input fails at step two. Neither reaches the
activity insert. If activity insertion itself fails, PostgreSQL rolls the business
change back.

## Format messages at the API edge

Register `GET .../issues/{issue}/activity` and authorize it with `IssueScope`. Query
events in chronological order and left join the actor name. Decode metadata, then use
the event type to produce current interface copy:

```php
$message = match ($row['event_type']) {
    'issue.created' => "{$actor} created the issue.",
    'status.changed' => "{$actor} changed status to {$metadata['to']}.",
    'priority.changed' => "{$actor} changed priority to {$metadata['to']}.",
    'comment.added' => "{$actor} added a comment.",
    default => 'Issue activity changed.',
};
```

The database retains facts; this boundary owns human language. We can improve copy or
localize later without rewriting historical rows.

## Render the timeline in React

Create `resources/app/activity-data.ts` with runtime parsing for `id`, `type`,
`message`, and `createdAt`. `ActivityPanel.tsx` loads the authorized collection and
shows an empty state, failure state, or ordered timeline. Mount it on the issue detail
page beside comments.

Use a real ordered list and visible message text. The line and dots are decoration;
the event remains understandable without color or layout.

## Prove failure creates no false history

The backend test creates one issue and sees `issue.created`. It submits invalid
priority, repeats a status change, changes priority and due date, and adds a comment.
The exact event sequence contains only five meaningful events. It then tries the
status route as an outsider, receives 404, and proves the count remains five.

The React test receives two already-formatted events and asserts their visible order.

```bash
php artisan test tests/Feature/IssueApiTest.php tests/Feature/WorkspaceAuthorizationTest.php
npm run typecheck
npm run lint
npm test -- --run resources/app/issue-workflow.test.tsx
```

The backend passes 29 tests with 208 assertions. The React workflow passes twelve
tests. Our tracker now supports real team ownership, planning, organization,
conversation, and an honest history of changes. The next batch can build search,
filtering, pagination, and deliberate server-state caching on top of workflows that
are finally worth finding and synchronizing.
